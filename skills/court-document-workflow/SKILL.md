# 法院文书到日历

本目录是**源码集成预览**，不是复制后即可启用的新电脑安装包。先按[运行与验收](references/operations.md)配置接收者环境、真实依赖、权限和处理范围，并完成验收；不能将发布者电脑上的运行结果当作接收者已安装成功。公开包不含用户台账、原件、凭据或定点修复授权。

## 先确定范围

- 明确短信接收日期下限、历史补查范围、同案历史信息只读范围、原件与状态目录、目标日历及报告目录。接收日期与案号年份分别处理，不继承发布者授权；当前源码仍有 2026 年起的收件限制及历史补查常量，先核对是否符合接收者范围，必要时修改代码并验证，不能只改说明就宣称支持任意年份。
- 明确允许新增、补齐、修改已有日程的范围。历史收到及到期补齐须在授权内；过去开庭等活动默认不重新建立。旧日程删除、合并后移除重复项、远端失效附件替换另按具体计划和授权处理，不继承任何其他使用者的授权。
- 保留人工标题信息、自动区块外备注和既有提醒。无法可靠区分人工内容时保留并列待核，不静默覆盖。不得改写原件、清空队列或以恢复旧备份覆盖新回执。
- 不因读取本技能而创建定时任务、修改系统隐私设置、向第三方发送消息或上传案件原件。网站辅助与后台服务分别配置。

## 每轮执行

1. 读取持久队列、模型健康状态和已有日历回执，先恢复未完成回读。下载成功、扫描追平、进程退出正常均不等于 OCR、审查或日历完成。
2. 显式读取已安装 `mineru-document-parsing` 及实际所用 OCR 技能，按准确率选择引擎。所有文书均 OCR，包括有文字层的 PDF；只可按相同内容 SHA 复用完整成果。保存逐页正文、页数及质量状态；异常页补识，关键内容不清时实际查看原图并留记录。第二引擎文字不能冒充视觉核验。内存阈值约束及依赖见[运行与验收](references/operations.md)。
3. 全文检查所有页的办理日期、期间、地点和条件，不限文件名含“传票”的文件。开庭、证据交换、调查、鉴定、缴费、举证、上诉、履行、保全届满及续保等分别识别；历史事实、落款等列入日期清单并说明不登记理由。OCR 为 partial 时如实保留，不以局部识别成功标为全文完成。
4. 按完整案号关联同案历次原件和获授权的历史短信，不能只凭尾号、同名或同一客户串案。主体优先取正式文书及明确关系语句；“某某您好”、收件人或被传唤人不自动证明诉讼角色。逐人保留来源，区分审级及角色变化。历史读取失败要说明覆盖缺口，不改变下载游标或扩大补查范围。
5. 涉及期限规则时，显式读取 `trial-scheduling-and-deadline-monitoring`、`legal-article-retrieval`、`legal-norm-validity-check`；跨材料综合时读取 `multi-document-summarization`。实际调用适配法律 MCP，关键规则原则上用两个独立来源交叉核验。查清适用版本、起算事实及官方节假日；缺口留待核，不以缓存或模型常识代替。详见[来源要求](references/source-requirements.md)。需要实体案件分析时另启用 `legal-case-analysis-orchestrator` 并执行其显式加载清单。
6. 使用 GPT-6.1 Sol（`gpt-6.1-sol`）及 `max` 完成全文审查和独立复核，全流程不得静默降档或换模型。模型只提出结构化结果或白名单法律查询请求，控制器执行法律工具并独立校验；本机工具执行通道关闭，出现越权工具尝试即拒绝该轮。真实输入输出约定见[审查协议](references/review-prompt.md)。
7. 写入前核对原件 SHA、完整页覆盖、原句、主体来源、真实收到关联、日期计算、授权范围及已有 UID。全文审查与独立复核通过后才登记确定活动或到期；不能用正则未命中代替完整阅读。只核材料类型和实际收到的局部入口与全文状态严格分开。
8. 串行去重写入后，按 UID 重新读取标题、时区及全天范围、地点、简洁备注、每份 PDF 内容 SHA 和提醒。文本已写但附件或提醒未核实仍为未完成；保留 UID 和 partial 回执，重试先只读检查，避免重复登记。

## 双节点与显示规则

- 对本次具体期限材料，在真实收到当天登记收到节点，在已确定到期当天登记独立到期节点，并为到期节点设置提前 7 日提醒。收到节点不另加期限提醒，保留默认及人工提醒。两个节点的备注均列收到日期和到期日期。
- 同完整案号、同一真实收到日期的材料合为一个收到日程，包含全部已核验成员及 PDF；不同到期事项分别保留。后续批次并入旧组全部材料、截止和待核项，不能由最后一份覆盖。相同 SHA 的重复通知不重新设收到日或起算日。
- 收到日期仅由程序验证本件路径、SHA、下载清单及送达通知标识后取得；模型不能猜收到日。收到记录不自动等于法律送达、生效或实际冻结。也不能一概排除短信记录，应核实具体电子送达条件与本件关联。
- 到期未知但实际收到已核实，可只登记真实收到节点，备注写“核实起算日期及具体期限后补录”；完整缺口保留待核清单。不能把收到日、处理日或归档周当作截止日，也不建虚构“待核到期”日程。没有真实收到绑定则继续待核。
- 保全届满与续保申请截止分开核验；区分实际冻结、轮候及已解除状态。提前 7 日提醒不代替更早的申请要求。已完成或已被后续文书解决的阶段不能再作为未完成事项。
- 标题为“完整案号｜已核实双方｜具体事项”。原被告明确写“甲诉乙”，其他双方或角色未明写“甲与乙”。每侧多人可用首个已确认姓名加“等”，只有一人不加“等”；完整名单与角色保留备注及审计。一方未知如实标注，不补猜。
- 保留“摇号选取鉴定机构”“二审新证据举证截止”等具体事项，不退化为“日程”或泛称。新材料补齐主体后，在授权范围内同步更新既有相关日程；无变更依据不改日期、地点。
- 备注只保留收到/到期日期、完整主体及角色、办理要点和来源页；长原句、法律检索、算式、错误详情和证据路径留后台审计。不要把截断的长待核原因塞进日历。
- 收到和到期节点均实际附对应 PDF，跨文书日期或起算依据也需附上。备注里的文件路径、`file://` 链接或附件标志不能当作真实 PDF 附件验收。

## 恢复与验收

全文 `review_status`、局部收到 `receipt_review_status`、日历写入及回读状态分别记录。局部收到入口必须有真实材料页核对，不得写 `all_pages_reviewed:true`，不得改变全文或 OCR 状态。旧规则的 ready 方案须按当前规则重审，不直接写入。

附件助手通过正常 macOS 应用入口运行，不能将应用内二进制的直接子进程读取结果等同应用权限。启动成功不代表业务成功；必须检查真实回执。partial 恢复先只读核对原方案，满足后补记回执，不先重写或重复加附件；不可读、确实缺失、人工内容变化及缺提醒分别保留失败原因。

附件验收分三层报告：**本机真实附件及 SHA 已核实**、**云端地址已登记**、**另一台 Mac 实际接收已核实**。前一层不能证明后一层；不记录或公开远端附件访问 URL。普通同步重试只读，不重复追加附件。替换修复须核对唯一对象、当前完整附件清单、准确原件和具体授权，保留其他内容；本发布包不含任何私案专用修复入口。

批量检查从指定日历的实际法院事项与新旧台账并集出发，不只检查新版本台账。分别报告已修改、原已符合、缺原件、主体待核、法律起算待核、附件本机/云端/跨设备状态，以及失败保留项。不能把收到节点完成称为全文或全部期限完成。
